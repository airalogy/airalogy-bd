# 软件版本管理

## 版本号

`package.json` 的 `version` 是唯一的软件版本来源，统一使用 `x.y.z`，不使用 `dev`、`alpha` 等后缀。界面版本由构建过程自动读取，不能单独修改生成的版本信息或借用业务工作区的版本。

- `x`：重大不兼容变更。
- `y`：兼容现有使用方式的功能扩展；增加时把 `z` 归零。
- `z`：兼容的修复和小幅改进。

**1.0.0 是首次发行基线**，功能、配置和数据格式以该版本文档为准。版本号本身不表示已经正式发布或部署。

后续修复使用 `1.0.1`、`1.0.2`；兼容的功能扩展使用 `1.1.0`、`1.2.0`；需要调整既有使用约定的不兼容变更使用 `2.0.0`。兼容性约定从 `1.0.0` 开始，覆盖对外接口、配置和业务数据的读写与恢复。发生格式变化时提供明确的备份、转换和回滚步骤，不静默丢弃用户资料。

公开更新记录从 `1.0.0` 开始。代码提交用于开发追溯；业务资料的修改历史、审计和备份属于产品功能，分别独立保存。

## 日常开发

一般提交先记入 `CHANGELOG.md` 的 `Unreleased`，无需每个提交都增加版本号。需要形成一个可识别的交付版本时，统一更新 `package.json`，并将本批改动整理到更新记录顶部的对应版本和日期下。

运行 `pnpm version:check` 检查版本格式、更新记录的对应关系和日期；`pnpm test` 已包含此检查，后续继续执行资料校验、代码检查、构建和测试。页面同时展示构建标识，可区分同一版本号下尚未发布的本地改动。

`pnpm-lock.yaml` 不单独记录根项目版本；只改根项目版本无需重算依赖。依赖发生变化时，必须同步锁文件并重新验证。

## 正式发布

提交、推送、打标签、创建 Release、发布安装包或镜像、部署是独立步骤。普通的“提交、推送”只更新代码分支，不自动触发后面的步骤。

正式发布获授权后：

1. 在干净的检出目录核对版本与更新记录，完成自动测试、适用的真实服务联调及恢复演练。
2. 在已验证的同一提交创建带说明的 `vX.Y.Z` 标签，记录发布说明；已发布标签不可移动或覆盖。
3. 从该提交构建安装包或镜像，记录版本、提交号和镜像摘要，验证实际产物的安装与运行。
4. 部署前保存备份、旧版本标识及回滚步骤，部署后核对实际运行版本。

需要修正已发布版本时发布新版本，不在旧版本号下替换内容。使用源码运行时，页脚的“构建来源：本地源码”表示运行来源，与 `x.y.z` 版本号及是否正式发布分别记录。
