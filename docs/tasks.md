# 事项待办

在主导航的“待办”中集中查看当前有权访问的事项行动，也可在事项详情中查看和维护同一份待办。默认显示未完成事项；可切换“我的待办”、已完成、已取消，按事项、负责人、期限或关键词筛选。未完成列表按截止日期排序，未设期限的排在后面。

## 记录与完成

每条待办包含内容、Markdown 说明，以及可选的负责人、截止日期和来源进展。状态有待处理、进行中、等待对方、已完成、已取消。负责人从能编辑该事项的已启用团队账号中选择；不自动将会议参与人设为负责人，也不因分配待办而授予事项权限。本机模式使用“本地操作”身份。

勾选待办可直接标记完成。展开待办后选择“完成并填写结果”，可补充完成备注。创建、编辑和完成均记录实际操作账号与时间，修改与完成记录中可查看当时内容。重新打开已完成待办时清除当前完成标记，原完成备注仍保留在历史版本中。

完成时可以主动勾选“同时记录业务进展”，填写实际发生日期、标题、摘要和已有参与人。这条进展与待办原子保存；任一校验失败时均不落盘。适用于已发送材料、收到回复等实际发生的动作。

待办本身不修改原会议、沟通正文、参与人或原记录的更新人，也不改变最近业务活动日期，不进入动态日历、不计为一次会议或沟通。仅主动新增的业务进展影响业务时间线。既有“下一步”继续保留，可选择“转为待办草稿”后修改并保存，不会自动生成承诺、负责人或期限。

## 权限与历史

查看和编辑沿用所属事项权限；只读成员可以查看，编辑成员可维护获授权事项的待办。负责人调整不会改变账号访问范围。成员停用或失去事项权限后不能新分配，但原有分配和历史保留，避免丢失责任记录。

事项移入回收站时，其待办退出全局列表和统计并停止修改，恢复事项后重新显示。来源进展移入回收站时，待办保留并标明来源归档状态。历史工作区显示当时待办内容；单条待办历史同样受当前事项权限限制。完整备份包含待办和历史，可恢复到独立工作区。

## MCP

沿用外部 AI 连接的查询、提交草稿、管理员直接保存模式，无需新增接入配置。

| 工具 | 用途 |
| --- | --- |
| `search_tasks` | 跨获授权事项或在指定事项中查询；默认未完成，可筛选状态、负责人、期限与关键词；`scope: mine` 表示当前账号负责 |
| `read_task` | 读取待办、完整字段和版本；不传 `id` 时取得指定事项的新建版本；支持历史快照 |
| `task_assignees` | 返回能编辑此事项的已启用账号 ID 和姓名，不含联系方式或其他事项权限 |
| `task_history` | 查询修改、完成及重新打开的历史；传 `version` 读取当时内容 |
| `submit_task` | 提交新建或修改草稿，由本人在网站确认 |
| `save_task` | 仅管理员明确选择直接保存的连接可正式保存 |

写入前先查询查重，读取当前版本；修改使用待办 ID 和版本，新建使用事项待办集合的版本。`request_id` 是至少 16 位的唯一请求编号；重试保留原编号与内容，结果不确定时回读核对，不更换编号重试。相同事项、相同来源、相同标题的未完成待办会阻止重复创建。

`changes` 支持 `title`、`body`、`state`、`assignee_id`、`due_date`、`source_progress_id`、`completion_note`。作者、更新人、完成人及时间由服务端按实际账号保存，不接受客户端冒名字段。未提供负责人或期限时保持为空。

同时记录业务进展时，额外传入 `completion_event`，包含最新 `read_task` 返回的 `progress_revision` 和与网页一致的进展 `payload`。仅允许本次转为已完成时使用；不自动把待办说明或完成备注当作实际业务事件。参与人复用所属事项的已有档案，需要新增人员时使用常规进展录入流程。
