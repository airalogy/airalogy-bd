# 公开代码检查

本仓库保存产品源码、通用模板和虚构示例。真实工作区、联系人、合同、融资资料、账号数据库、模型密钥、运行日志和备份应保存在独立的私有目录。

## 每次对外提供代码前

1. 检查将要提交的文件清单与差异。确认示例人员和机构均为虚构，联系方式使用示例地址；不要将真实业务记录改名后当作测试数据。
2. 执行 `pnpm publication:check` 和 `pnpm test`。基础检查会拒绝私有目录、附件与数据库路径、个人主目录、非示例邮箱、私钥和生成的构建身份；只报告文件位置与问题类别，不输出敏感值。它不能识别所有商业秘密，也不替代密钥扫描。
3. 用本机密钥扫描工具检查实际交付快照，例如 `gitleaks dir /path/to/export --redact`。不要把待检查源码或业务资料上传给第三方扫描服务。
4. 从已审查的提交导出，而非复制整个工作目录。用 `git archive HEAD` 生成不含 Git 历史的源码快照，再运行 `node scripts/check-publication.mjs --directory /path/to/export`。复核隐藏文件、符号链接及最终压缩包清单。
5. 安装包的 `files` 使用源文件类型白名单，避免整个目录中的私有文件被带入。根目录 `.npmignore` 不能覆盖 `files` 的包含规则（见 [npm 官方说明](https://docs.npmjs.com/cli/configuring-npm/package-json/#files)）。如需提供安装包，在干净快照中执行 `npm pack --ignore-scripts`，解包后重复检查。容器构建使用 `.dockerignore` 的源文件白名单与隐私排除规则；镜像实际发布前仍须检查构建产物，不能仅根据源码检查推断镜像安全。
6. 核对提交作者邮箱与将要公开的代码历史，确认其中没有私有资料。使用 GitHub 提供的 noreply 邮箱可避免公开个人联系邮箱。

`.gitignore` 不会移除已跟踪文件；自动检查包含这些文件。历史中曾提交敏感资料时，应按实际情况处置历史和撤销凭据；当前快照没有发现问题不代表旧历史也没有问题。

## 公开内容约定

- 安装来源使用公司包名和公司仓库地址；文档使用通用路径与虚构示例。
- 部署示例使用 `bd.example.com`，测试机构和人员不引用真实业务关系。
- Git、安装包和容器上下文排除私有运行状态、密钥、数据库、附件与备份。
- Airalogy BD 与杭州渊楠科技有限公司是公开产品名称和版权归属，应保留在许可及产品说明中。
- 源码和导出文件检查不等同于完整安全审计、真实云服务验收或生产部署；分发前应验证实际产物。
